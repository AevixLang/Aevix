# Участие в разработке Aevix

Спасибо за интерес к проекту! Ниже приведены правила, которые помогают поддерживать здоровье кодовой базы.

## Контракт тестирования

`aevix selftest` — единственная проверка перед любым слиянием в `dev`.

- **Возможность без теста не существует.** Если вы добавляете возможность языка, встроенную функцию или изменение поведения, должен быть как минимум один положительный тест (возможность работает) и, где применимо, как минимум один отрицательный тест (компилятор корректно отклоняет неправильное использование).
- **Отрицательные тесты остаются навсегда.** После фиксации отрицательного теста (например, «возврат из эпохи отклоняется») удалять его молча нельзя. Если язык меняется и ранее отклонённый шаблон становится допустимым, тест обновляется под новое поведение, а не удаляется.
- **`aevix selftest` обязан быть зелёным перед любым слиянием.** Без исключений, включая срочные исправления.

## Как мы работаем

### Ветки

```
main   = только релизы (коммиты слияния с `--no-ff` + метки версий)
dev    = основная линия разработки (здесь хранится вся история)
feat/* = ветки возможностей (ответвляются от dev, вливаются обратно через `--no-ff`)
```

- Практически вся работа идёт в `dev` или в ветках `feat/*`.
- `main` изменяют **только** при выпуске релиза.
- `dev` никогда не переписывают и не удаляют.

### Сообщения коммитов

Одна строка, английский язык, первая буква строчная. Префикс Conventional Commits с необязательной областью:

```
feat(backend): add sema stage
fix(cli): inherit stdin for input()
test: cover arena-backed slices
docs: document compound assignment
chore: ignore out.txt artifact
style: unify code comments
```

Типичные области: `(frontend)`, `(backend)`, `(cli)`, `(tools)`.

В обычных коммитах не бывает многострочных сообщений. Русский язык в сообщениях коммитов не используется.

### Выпуск релиза

```bash
git switch dev
aevix selftest                              # всё должно быть зелёным

git switch main
git merge --no-ff dev -m "release 0.x.x: short summary"
git tag -a v0.x.x -m "release 0.x.x"
git push origin main --tags
```

`--no-ff` обязателен при слияниях релиза, чтобы слияние было видно в `git log --graph`.

## Стиль кода

- **C++:** `// === Section Header ===` для крупных разделов; блочные комментарии `/** ... */` для документирования функций. Английский язык, без точки в конце однострочного комментария.
- **Go:** короткие английские комментарии над строкой, которую они поясняют; объясняется *почему*, а не *что*.
- **Python:** стандартные строки документации для модулей; комментарии объясняют *почему*.

## Эталонный набор

`frontend/tests/corpus/` хранит действующий контракт вывода языка. Каждый файл `corpus/*.aev` в паре с `corpus/*.golden` собирается полным конвейером (фронтенд → бэкенд → LLVM → clang) и запускается **без аргументов и с пустым стандартным вводом**; его стандартный вывод должен точно совпадать с `.golden` (проверяется в `frontend/tests/test_golden.py`, входящем в `aevix selftest`). Файлы без `.golden` тест игнорирует.

Если изменение намеренно меняет вывод, пересоздайте эталоны в том же коммите:

```bash
venv/bin/python tools/gen_golden.py
```

## Измерение производительности

`aevix bench` собирает небольшой (`examples/test.aev`) и синтетически большой (цепочка из 2000 переменных) исходный файл через конвейер, печатает время выполнения каждого этапа и дописывает строку базовых измерений с датой в `notes/benchmarks.md` (локальный файл, игнорируемый Git). Он служит для ручной оценки производительности парсера и генератора кода и **никогда** не запускается внутри `aevix selftest`.
