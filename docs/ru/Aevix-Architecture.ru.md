# Системная архитектура Aevix

Этот документ описывает внутреннее устройство и техническую реализацию конвейера компилятора Aevix.

---

## Обзор системы

Aevix использует многоэтапный конвейер с компонентами на разных языках, чтобы совместить быстрое прототипирование возможностей языка с экстремальной производительностью бэкенда.

**Поток данных на верхнем уровне:**
`Исходник (.aev)` → `Фронтенд (C++)` → `AST (JSON v6)` → `Семантика (C++)` → `Генерация кода (C++/LLVM)` → `LLVM IR` → `Машинный код`

---

## Разбор компонентов

### 1. Фронтенд (C++ с запасным фронтендом на Python)

Фронтенд преобразует человекочитаемый исходный код в типизированное JSON-дерево AST.

- **Лексер**: ручной токенизатор (`frontend/cpp/src/lexer.hpp`), поддерживающий все ключевые слова, операторы и литералы.
- **Парсер**: рекурсивный спуск (`frontend/cpp/src/parser.hpp`), создающий AST на основе вариантов (`ast.hpp`).
- **Разрешение импортов**: рекурсивная загрузка модулей с обнаружением циклов, поддержкой `AEVIX_PATH` и разрешением пакетов через `aevix.lock` (`importer.hpp`).
- **Сериализация JSON**: выводит `ast.json` с `SCHEMA_VERSION = 6` (`json_out.hpp`).

**Почему C++:**
в 20 раз быстрее фронтенда на Python. Устраняет зависимость от Python на основном пути сборки.

**Запасной фронтенд на Python:**
устаревший фронтенд на Python+Lark (`frontend/src/`) по-прежнему доступен, если двоичный файл C++ не собран. Он использует грамматику Lark EBNF (`frontend/grammar/aevix.lark`) и выдаёт идентичный JSON.

### 2. Статический анализ (семантика)

Семантический анализатор проверяет AST перед генерацией кода.

- **Проверка типов**: сравнения с учётом ширины, проверка типов операторов, правила преобразования типов фиксированной ширины.
- **Проверка областей видимости**: поиск переменных и функций по идентификатору, отклонение повторных объявлений.
- **Анализ выхода за пределы эпохи**: не позволяет значениям, выделенным в арене, пережить свою эпоху.
- **Проверка параметров по ссылке**: требование lvalue, отклонение псевдонимов, правило единственной изменяемой ссылки.
- **Проверка оператора return**: значения, связанные с ареной, отклоняются при выходе из эпохи.
- **Совместимость присваиваний**: обнаружение несоответствия типов, проверка составного присваивания.

### 3. Бэкенд (C++ и LLVM)

Бэкенд преобразует проверенный AST в LLVM IR.

- **Чтение JSON**: десериализует AST во внутреннее представление C++ (`json_reader.cpp`).
- **Генератор кода**: использует LLVM IRBuilder для создания оптимизированного IR для всех узлов AST (`codegen.cpp`).
- **Среда выполнения**: библиотека на C (`aevix_runtime.c`), предоставляющая выделение памяти в арене, сохранение и восстановление эпох, проверку границ, ввод-вывод, строковые операции и встроенные функции.
- **Кодогенерация с учётом ширины**: создаёт инструкции, соответствующие ширине типов фиксированного размера (`i8`–`u64`, `f32`/`f64`).

### 4. Инструментарий (Go)

Высокоуровневый слой оркестрации, отвечающий за удобство разработки.

- **Консольная утилита**: один двоичный файл (`aevix`), оборачивающий весь конвейер: фронтенд → семантика → генерация кода → opt -O2 → llc → clang.
- **Запуск тестов**: выполняет набор интеграционных тестов с параллельным выполнением и наглядным выводом.
- **Конвейер сборки**: управляет вызовом фронтенда C++, семантики, бэкенда и компоновщика.

## Цикл разработки

### Стандартный конвейер сборки

1. **Разбор**: `aevix-frontend input.aev` → `ast.json`
2. **Анализ**: `aevix-sema ast.json` → проверенный AST
3. **Генерация**: `aevix-backend ast.json` → `output.ll`
4. **Оптимизация**: `opt -passes=default<O2> output.ll -o output.opt.ll`
5. **Ассемблирование**: `llc output.opt.ll -o output.o`
6. **Компоновка**: `clang output.o runtime.o -o program`

### Быстрое прототипирование

При добавлении новой возможности языка:
`Обновить грамматику и лексер` → `Добавить узел AST` → `Реализовать проверку в семантике` → `Реализовать генерацию LLVM` → `Проверить через aevix selftest`.

## Планы развития и технический долг

- [ ] **Полный анализ выхода за пределы эпохи**: проверка на уровне параметров.
- [x] **Оптимизация горячих регионов**: атрибут `hot` для функции, метаданные векторизации и развёртывания циклов, слоты с выравниванием 64 байта, предвыборка горячих выделений памяти, этап конвейера `opt -O2`, который их использует (циклы векторизуются); `epoch` внутри запрещён.
- [ ] **Преобразования SOS**: автоматическое продвижение данных на стек и преобразование в SIMD.
- [ ] **Контекстуальный полиморфизм**: генерация варианта функции для каждого места вызова.
- [ ] **Доказуемая безопасность**: проверка инвариантов во время компиляции.
- [ ] **Поддержка пространств имён**: имена в области модуля вместо плоского глобального объединения.
- [ ] **Именованные литералы структур**: синтаксис `Point { x: 1, y: 2 }`.
- [ ] **Интерфейс AST**: оценка Protobuf как замены JSON для больших файлов.

## Технические спецификации

| Компонент | Технология | Роль |
| :--- | :--- | :--- |
| Грамматика | Lark (EBNF) | Эталон синтаксиса |
| Фронтенд | C++17 (основной), Python (запасной) | Лексический и синтаксический разбор, генерация AST |
| Промежуточное представление | JSON (схема v6) | Связь фронтенда и бэкенда |
| Статический анализ | C++17 | Проверка типов, областей видимости и выхода за пределы эпохи |
| Генерация кода | C++17 + LLVM | Генерация IR |
| Среда выполнения | C | Арена, эпохи, встроенные функции, ввод-вывод |
| Оркестрация | Go | Консольная утилита и запуск тестов |
